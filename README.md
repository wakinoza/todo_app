# Spring Boot 3 Todo アプリケーション

本プロジェクトは、以前公開した「Unit Test Update Edition」をベースに、アーキテクチャを従来の Servlet/JSP から Spring Boot 3 (Spring Framework 6) へと変更し、セキュリティ、堅牢性、UI/UXを改良したアップデート版です。

これまでのテスト駆動の知見を活かしつつ、プロダクション環境を見据えた本格的なバックエンド構成を構築しました。

## 🧪 アップデートの概要
従来のアーキテクチャから脱却し、実務基準のインフラ・セキュリティ・フロントエンドを統合するために、以下の実装およびリファクタリングを行いました。

### 1. Spring エコシステムの全面導入によるアーキテクチャ刷新
* **Spring Boot 3 / DI・AOPの活用**: 柔軟な依存性注入（DI）によりオブジェクト間の結合度を下げ、コンポーネントの責務を明確に分離しました。
* **Spring Data JPA**: データベースアクセス層を共通化し、型安全で保守性の高いデータ永続化処理を実現しました。

### 2. Spring Security によるエンタープライズ基準の防衛
* **フォーム認証とBCryptハッシュ化**: ユーザー認証機構を Spring Security へ委ね、パスワードは BCrypt で強固にハッシュ化して MySQL に保持する安全な設計へ移行しました。
* **CSRF防衛とセッション管理**: クロスサイトリクエストフォージェリ（CSRF）やセッション固定攻撃に対する防御を組み込み、Webアプリケーションの基本脆弱性を全方位でカバーしました。

### 3. Logback による実務運用のシミュレーションと脆弱性対策
* **ログローテーションの自動化**: `RollingFileAppender` を導入。ファイルサイズや日付制限による自動ローテーションを施し、サーバー容量枯渇リスクに備えました。
* **ログインジェクション対策**: 自由入力値（Todo項目など）がログに出力される際の構造化を行い、不正な改行コード注入によるログ改ざん（ログインジェクション）を無効化しました。

### 4. Bootstrap 5 による UI/UX の全面刷新
* **CSSフレームワークの導入**: Bootstrap 5 を用いた視認性の高いUIへと生まれ変わらせました。

## 🚀 起動手順 (Docker)
Dockerがインストールされた環境であれば、以下の手順で動作確認が可能です。MySQLの初期化・接続受付完了を自動的に検知してアプリケーションが立ち上がる安全なコンテナオーケストレーションを組んでいます。

1. リポジトリをクローン
```bash
git clone https://github.com/wakinoza/todo_app
cd todo_app
```

2. 環境変数の準備
.env.example をコピーして .env を作成し、必要なデータベース接続情報を設定してください。
```bash
cp .env.example .env
```

3. コンテナの起動
```bash
docker compose up -d --build
```

4. アクセス
ブラウザで http://localhost:8080/login にアクセスしてください。自作のカスタムログイン画面が表示されます。
以下の情報を入力すると、ログインおよびTodo操作が可能です。

ユーザー名： yamada

パスワード： yamada_password

5. テストの実行
コンテナ外のローカル、またはMaven環境があれば、以下のコマンドで独立した単体テストが可能です。
```bash
mvn test
```

## 🧠 苦戦した点


* **リポジトリ移行時における `.gitignore` 上書きと重要情報の誤コミット**
  Servlet構成からSpring Boot構成へリポジトリを統合・移行する際、IDE（Eclipse）が生成したデフォルトの `.gitignore` を上書きコピーしてしまい、除外指定していたはずの `.env` が消去されてしまいました。一括コミットの直後、IDE上で `.env` のファイル名の色が「Git追跡中」に変わったことに気づき、.envの誤コミットが発覚しました。
  
  **【対策】** 幸いリモートへ `push` する前であったため、過去の歴史そのものを改変して機密情報を完全に消し去るために **`git rebase -i`（インタラクティブ・リベース）** を実施しました。対象コミットを編集状態にし、インデックスから `.env` を完全に排除してコミットを再構成しました。気を付けていても一瞬のオペレーションミスで情報漏洩が起きる恐怖を、身を以て学びました。

* **Spring Security導入時におけるデフォルト画面の起動と認証拒否問題**
  独自にスタイリングしたログイン画面（`login.html`）を設置したものの、URLアクセス時に Spring Security が自動生成する既定のログイン画面が強制表示される現象が発生。さらに、そ正しいログイン情報を入力しても通信が遮断され、ログイン不能になる二重の挙動に悩まされました。
  
  **【対策】** 調査の結果、Securityによる自動保護機能と、**CSRF（クロスサイトリクエストフォージェリ）防衛のワンタイムトークン不備**が原因であることを突き止めました。`SecurityConfig` で自作の `/login` パスを認証の入り口として明示的にマッピングし、HTMLフォームの `action` をThymeleaf式（`th:action="@{/login}"`）に書き換えることで、安全なCSRFトークンが自動注入される構造へ改善。セキュリティ検問を正しく突破させることに成功しました。

* **Dockerの非root実行（一般ユーザー）によるログ出力権限エラー**
  コンテナセキュリティ向上のため、実行ユーザーを一般ユーザー（`USER 1000`）へ切り替える設計に挑戦しました。しかし、コンテナ内の `/app` ディレクトリが root 所有のままだったため、Spring Boot起動時に Logback がログ保存用の `logs/` フォルダを自動生成できず、`FileNotFoundException` でJavaプロセスが停止する状況に直面しました。

  **【対策】** Dockerfileのステージ2において、一般ユーザーに切り替える直前のroot権限があるタイミングで `RUN mkdir logs && chown -R 1000:1000 /app` を実行し、あらかじめ権限を譲渡しておくことで、セキュリティと機能性を両立させたコンテナ環境を確立しました。
